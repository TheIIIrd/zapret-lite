# Разработка

## Дерево

```
bin/zapret-lite        менеджер
lib/common.sh          общие функции (POSIX sh)
install.sh             установщик
uninstall.sh           деинсталлятор
config/*.in            шаблоны, подставляются при установке
systemd/               юнит проверки обновлений и drop-in
strategies/*.conf      генерируется, руками не править
vendor/flowseal/       снимок релиза flowseal + MANIFEST.sha256
vendor/zapret/         пин апстрима по хешу коммита
tools/                 конвертер и синхронизация
tests/                 bats
```

## Перед первым релизом

`vendor/zapret/zapret.lock` уже заполнен: zapret v72.13, коммит
`87e0586`. При смене версии обновляйте оба поля.

Бинарники берутся из официального релиза автора (17 архитектур, включая
`linux-arm64` и `linux-arm`), а не собираются нами.

Проверок две. `sha256sum.txt` автора перечисляет файлы **внутри** архива,
путями вида `zapret-v72.13/binaries/linux-arm64/nfqws`, поэтому сверка
запускается из каталога, куда архив распакован — на v72.13 это 74
записи. Затем у бинарника спрашивается версия:

```
github version v72.13 (87e058624c72863db53bdaf7fb6f16576dddb6ab)
```

Коммит вшит в сам файл, и сверка с ним прямее, чем сравнение дерева
исходников: тег можно передвинуть, эту строку — нет.

Учтите: релизные бинарники собраны **без** `-DUSE_SYSTEMD`, то есть без
`sd_notify`. Нам это безразлично — шаблон `nfqws@.service` с
`Type=notify` мы не используем, служба поднимается через init-скрипт.
Если он вам зачем-то понадобится, собирайте из исходников целью
`make systemd`.

## .gitignore: не заменяйте шаблоном

Шаблон GitHub для Python содержит строку `lib/`. Если он попадёт в
репозиторий, `lib/common.sh` не будет закоммичен — и всё развалится
разом: shellcheck не найдёт файл, все bats-тесты упадут на `cp`,
установщик не запустится.

Наш `.gitignore` содержит явные `!lib/` и `!bin/`, которые это
переживают. Если что-то всё же пропало:

```sh
git check-ignore -v lib/common.sh
git status --ignored --short
```

Первый шаг CI проверяет наличие всех обязательных файлов и падает с
понятным сообщением, а не через полсотни чужих ошибок.

## Тесты

```sh
bats tests/            # число тестов растёт, точное значение печатает bats
bats tests/lib.bats    # только модульные
```

Три набора:

| Файл | Что покрывает |
|---|---|
| `lib.bats` | функции `lib/common.sh` по отдельности |
| `converter.bats` | правила перевода `.bat` и проверки, валящие сборку |
| `install.bats`, `manager.bats` | сквозные сценарии установки и управления |

Модульные тесты нужны не для красоты. В `cmd_use` недопустимое имя
отсеивается ещё и проверкой существования файла, поэтому сломанный
`zl_valid_name` через сквозной тест незаметен — вторая линия защиты
маскирует первую.

Всё ставится в префикс `$ZL_PREFIX`. В этом режиме код к systemd не
обращается вовсе - юнит лежит под префиксом, настоящий systemd его всё
равно не видит, - поэтому root не нужен и настоящая система не
затрагивается.

`systemctl` намеренно НЕ подменяется. Подмена скрывала дефект: реальная
установка в префикс от обычного пользователя падала на «Failed to
connect to bus», а тесты этого не видели, потому что говорили с
заглушкой. Подменяется только `nft` - определение типа firewall
опирается на наличие команды.

Тестам нужны распакованные релизы flowseal. Путь задаётся переменной
`ZL_TEST_RELEASES` (по умолчанию `/home/claude/src/rel`, каталоги вида
`v1.10.2`).

Линт:

```sh
shellcheck -x -s sh -e SC2329 install.sh uninstall.sh bin/zapret-lite lib/common.sh
```

`SC2329` отключён потому, что команды вызываются через `case` по имени и
shellcheck считает функции неиспользуемыми.

## Сборка zapret из исходников

Нужна, если для вашей архитектуры нет готового бинарника в релизе.
Инструкция апстрима (`install_bin.sh:139` и раздел «Установка под
systemd» в его `docs/readme.md`):

```sh
sudo apt-get install make gcc zlib1g-dev libcap-dev \
                     libnetfilter-queue-dev libmnl-dev libsystemd-dev
git clone https://github.com/bol-van/zapret
cd zapret && git checkout 87e058624c72863db53bdaf7fb6f16576dddb6ab
make systemd
```

**Цель `systemd`, а не `all`.** Она добавляет `-DUSE_SYSTEMD` и
`sd_notify(READY=1)` (`nfq/nfqws.c:280`); без этого шаблон `nfqws@.service`
с `Type=notify` работать не будет. Мы этот шаблон не используем, но
собирать иначе, чем документирует апстрим, смысла нет.

Результат появляется в `binaries/my/`. Скопируйте этот каталог в
`zapret/binaries/my/` внутри комплекта: `install_bin.sh` проверяет `my`
первым в списке архитектур (`install_bin.sh:168`).

Самосборный бинарник на `--version` отвечает `self-built version <дата>`,
а релизный — `github version <тег> (<коммит>)`. Это нормально: версии
программно нигде не сравниваются.

## Ветки и выпуск

Две ветки: `unstable` для работы, `main` для проверенного.

```
работа -> unstable -> (CI зелёный) -> PR в main -> тег -> релиз
```

`ci.yml` срабатывает на push в любую ветку и на каждый Pull Request,
поэтому отдельно запускать его не нужно.

Синхронизация с flowseal открывает PR **в `unstable`**, а не в `main`:
чужие изменения проходят тем же путём, что и наши. Ветка задаётся
переменной `TARGET_BRANCH` в `sync-flowseal.yml` и параметром `target`
при ручном запуске.

## Запуск workflow вручную

Все три workflow имеют `workflow_dispatch`, то есть кнопку **Run
workflow** на вкладке Actions. Через `gh`:

```sh
gh workflow run ci.yml
gh workflow run release.yml
gh workflow run sync-flowseal.yml -f what=lists
gh workflow run sync-flowseal.yml -f what=both -f target=unstable
gh run watch
```

Кнопка появляется только когда файл workflow есть **в ветке по
умолчанию**. Пока изменения лежат в feature-ветке, запустить их вручную
нельзя — это ограничение GitHub.

Чтобы `sync-flowseal.yml` мог открывать Pull Request, в Settings →
Actions → General нужно включить **Allow GitHub Actions to create and
approve pull requests**.

## Теги и релизы

```sh
git tag -a v0.1.0-rc1 -m "первая проверяемая сборка"
git push origin v0.1.0-rc1
```

`git tag` создаёт метку **локально** и никуда её не отправляет. Событие
в Actions порождает именно `git push origin <тег>`.

Тег `-a` аннотированный: хранит автора, дату и сообщение, в отличие от
простого `git tag v0.1.0`. Для выпусков стоит использовать его.

Тег ставится **на коммит из `main`**, уже после мержа. Release-workflow
это проверяет и отказывается публиковать тег, не входящий в `main`:
иначе легко выпустить непроверенный код из `unstable` и заметить не
сразу.

Тег с дефисом (`v0.1.0-rc1`) публикуется как предварительный релиз: он
не становится «latest» и не подсовывается тем, кто зашёл за свежей
версией.

Запуск `release.yml` по кнопке **не создаёт релиз**: комплект
собирается, проверяется и выкладывается артефактом на 14 дней. Артефакт
годится только для собственной проверки — его скачивание требует входа
в GitHub, и он истекает. Раздавать людям нужно релиз.

Версии по semver. Пока проект не проверен на разных машинах, разумно
жить в `0.x`: это честно говорит, что совместимость может меняться.

Если тег поставлен по ошибке:

```sh
git push origin :refs/tags/v0.1.0   # удалить на сервере
git tag -d v0.1.0                   # и локально
```

Релиз при этом останется — его удаляют на странице Releases. Удалять
уже опубликованный тег, который кто-то мог скачать, не стоит: лучше
выпустить следующий.

## Синхронизация с flowseal

Вручную:

```sh
python3 tools/vendor-sync.py <каталог-релиза> vendor \
        --version 1.10.2 --zapret-version 72.13
rm -f strategies/*.conf
python3 tools/import-strategies.py <каталог-релиза> strategies
```

Автоматически: `.github/workflows/sync-flowseal.yml` дважды в неделю
проверяет релизы и списки и открывает PR **в `unstable`**. Автомержа
нет и не должно быть.

Дальше PR идёт обычным путём: ревью, мерж в `unstable`, CI, потом PR из
`unstable` в `main`. Отдельно возвращать что-то в `unstable` не нужно —
изменения там и появляются.

Если синхронизация всё же попала в `main` напрямую (например, её
запустили с `target=main`), верните это в `unstable` слиянием, а не
переносом отдельных коммитов:

```sh
git checkout unstable
git merge main
git push
```

Два источника обновляются независимо:

- релизы — стратегии и фейковые пейлоады, раз в 1-3 недели;
- `main` — списки, заметно чаще.

## Обновление пина zapret

Осознанная операция: новая версия движка может изменить поведение всех
стратегий разом.

1. Поменять `zapret_ref` и `zapret_version` в `vendor/zapret/zapret.lock`.
2. Прогнать CI — он пересоберёт nfqws и проверит, что
   `tools/nfqws-options.txt` совпадает с таблицей `long_options` в
   исходниках.
3. Если список опций изменился — файл перегенерируется тем же способом,
   каким его порождает CI.

Версия нашего zapret не должна быть **старше** движка, на котором собран
`winws.exe` в релизе flowseal: иначе стратегии могут использовать опции,
которых наш nfqws не знает. `vendor-sync.py` проверяет это и падает.

## Конвертер

`tools/import-strategies.py` — Python, а не shell: разбор кавычек,
экранирования cmd и диапазонов портов на shell получается хрупким.
В рантайме форка Python не нужен, инструмент работает только в CI.

Любая непонятная конструкция — ошибка, а не предупреждение. Молча
пропущенная опция означает конфиг, который ведёт себя не так, как
задумано, и заметить это можно будет только по неработающему обходу.

## Проверка на настоящей машине

`bats` покрывает логику, но systemd и firewall в нём подменены макетами.
Что проверяется только вживую:

- служба действительно стартует под настоящим systemd;
- drop-in применяется (`Restart` берётся из него, а не из юнита апстрима);
- правила firewall появляются и **полностью снимаются**;
- сосуществование с уже имеющимися правилами.

Скрипт автоматизирует механическую часть:

```sh
sudo ./tests/vm-check.sh /путь/к/распакованному/комплекту
```

Он снимает `iptables-save`, `ip6tables-save` и `nft list ruleset` до и
после, ставит, диагностирует, удаляет и сверяет снимки, игнорируя
счётчики пакетов. Работает ли обход, он не проверяет и честно об этом
пишет.

## Стиль

- POSIX sh во всём, что попадает на целевую машину: `/opt/zapret/config`
  читается через `/bin/sh`, а это dash на Debian и Ubuntu.
- Пробелов в путях быть не должно: init-скрипт раскрывает опции без
  кавычек.
- Комментарии объясняют **почему**, а не что. «Проверяем манифест» —
  бесполезно; «манифест проверяется до переключения, иначе повреждённое
  поколение станет текущим» — полезно.
- Каждая правка, найденная тестом, закрепляется тестом.

## Проверять тесты мутациями

Зелёный набор не значит хороший. Самый быстрый способ понять, что он
на самом деле проверяет, - внести дефект и посмотреть, заметят ли:

```sh
cp -r . /tmp/mut
sed -i 's/if missing and not wf_dynamic:/if False:/' /tmp/mut/tools/import-strategies.py
( cd /tmp/mut/tests && bats . )   # обязано покраснеть
```

Так выяснилось, что у конвертера - самой ценной части проекта - не было
тестов вовсе: можно было убрать снятие экранирования `^`, проверку
существования файлов и сверку портов, и сборка оставалась зелёной.
Стоит прогонять при каждой значимой правке логики.

## Два правила про тесты

**Тест обязан проверять то, что обещает названием.** Один такой уже
находился: назывался «doctor замечает записываемый посторонними
local.conf», а проверял строку про манифест поколения - потому что сама
проверка прав в префиксе отключена и сквозным тестом недостижима.
Вместо подгонки утверждения проверка была вынесена в функцию
`zl_group_or_world_writable` и покрыта модульным тестом на пятнадцати
режимах доступа.

Отсюда общее правило: **если поведение недостижимо из сквозного теста,
это признак, что его пора вынести в функцию**, а не повод ослабить
утверждение.

**Тест, который пропускается всегда, - это отсутствующий тест с зелёной
галочкой.** CI считает пропуски и падает, если их больше одного.
